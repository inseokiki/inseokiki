### 2026-08-27 — `c_Makefile`이 헤더 의존성을 추적하지 않아 구조체 변경 후 부분 재빌드가 ABI 불일치를 냄
**무엇**: `L1Config`(`config_parser.h`)에 필드 2개를 추가한 뒤 변경된 `.c` 파일만 재빌드됐는데(`c_Makefile`의 패턴 규칙이 `.c`만 prerequisite로 잡고 `.h`는 안 잡음), 헤더는 안 바뀐 것으로 보였던 `pusch.c`/`pbch.c`/`main.c` 등의 `.o`가 옛 구조체 레이아웃 그대로 남아있어 `lls_sim_c` 실행 시 즉시 SIGABRT(exit 134), 출력 하나 없이 크래시. `regression_test.sh`가 48개 중 40개를 "crashed"로 보고해 처음엔 새 코드 자체의 버그로 오인했음.
**왜**: 이 프로젝트 Makefile은 헤더 의존성 파일(`.d`)을 생성하지 않는 단순 패턴 규칙(`$(OBJDIR)/%.o: $(SRCDIR)/%.c`)이라, 공용 헤더(특히 `config_parser.h`의 `L1Config`처럼 여러 `.c`가 필드 오프셋으로 접근하는 구조체)를 바꾸면 `make`가 부분 재빌드로는 절대 못 잡는 조용한 ABI 불일치가 생김.
**적용**: 공용 헤더(특히 구조체 정의)를 수정한 뒤에는 `make -f c_Makefile clean && make -f c_Makefile`로 항상 전체 재빌드하고 나서 회귀 테스트를 돌린다. "코드는 맞는 것 같은데 크래시"가 나오면 새 로직을 의심하기 전에 먼저 clean 재빌드부터 시도한다.
**후속(2026-09-03)**: 근본 원인(헤더 의존성 미추적)을 `c_Makefile`에 `-MMD -MP` + `.d` 파일 include로 수정 — 헤더 변경 시 관련 `.c`가 이제 부분 재빌드로도 자동 포함됨(touch 테스트로 11개 파일 정확히 재컴파일 확인, 회귀 78/78 유지). 이후로는 매번 clean 재빌드를 수동 강제할 필요 없음 — 그래도 의심스러우면 clean 재빌드로 교차검증하는 것 자체는 여전히 안전한 습관.

### 2026-08-27 — 새 기능이 "의도한 물리적 효과를 안 보인다"고 결론 내리기 전에 실제 계산값을 직접 찍어봐야 함
**무엇**: `SPATIAL_CORR_XPOL`(교차편파 XPD 누설 상관) 구현 후 "rho, rho_xpol을 극단으로 올리면 rank-1 선택률이 오른다"는 가설을 standalone 검증 하네스로 확인하려 했는데, 오히려 rank-1 선택률이 0%로 유지되거나 더 떨어지는 반직관적 결과가 나옴. 로그/출력만 보고 "가설이 틀렸다"거나 "기능이 안 먹힌다"고 단정하지 않고, 채널을 수동으로 완전 rank-1(4열이 동일 벡터)로 구성한 별도 디버그 하네스를 만들어 `codebook.c`의 2×2 Gramian 중간값(A00/A11/A01/det)을 직접 출력해봄 — 그 결과 (1) `det`가 이론상 항상 `N0²` 이상 양수여야 하는데 부동소수점 뺄셈으로 음수가 될 수 있는 catastrophic cancellation 결함과, (2) `codebook_type1_sp_4port_rank1/rank2()`가 rank-1/rank-2 모두 컬럼당 동일한 `norm=0.5`를 써서 rank-2 총 송신전력이 rank-1의 2배(+3dB)가 되는 정규화 불일치, 2건의 기존 결함(내가 만든 게 아니라 이미 있던 것)을 찾음.
**왜**: 새로 추가한 코드가 기대한 물리적 결과를 안 보이면, "내 새 코드가 틀렸다" 또는 "물리적 가설 자체가 틀렸다"만이 아니라 "기존의, 지금까지 아무도 이 정도 극단값으로 실행해본 적 없는 코드 경로에 숨어있던 결함을 이번에 처음 노출시켰다"도 똑같이 유력한 가설이다. 표면(BLER/선택률 %) 관찰만으로 결론 내리지 말고 중간 계산값을 직접 찍어보는 게 훨씬 빠르게 진짜 원인에 도달함.
**적용**: 새 파라미터/기능이 예상과 다른 방향으로 움직이면, 먼저 결정론적인 극단/경계 입력(랜덤 대신 손으로 구성한 채널 등)으로 중간값을 직접 출력하는 최소 디버그 하네스를 만들어 원인을 좁힌다. 발견된 결함이 요청받은 작업 범위를 벗어나고(예: 기존 시뮬레이션 히스토리/실측치에 영향) 수정 파급도가 크면, 그 부분은 임의로 고치지 말고 사용자에게 발견 사실과 파급 범위를 구체적으로 보고한 뒤 진행 여부를 확인한다 — `tasks/todo.md`의 해당 항목 참조.

### 2026-07-15 — 작업 시작 전 git fetch/status 확인 누락으로 히스토리가 갈라진 사고
**무엇**: 다른 세션/기기에서 `PHY/common` + `PHY/lls_sim` + `PHY/ber_sim` 구조로 재구조화한 커밋들이 원격(`origin/develop`)에만 push되어 있었는데, 로컬에서 이를 모른 채 기존 평면 구조(`PHY/src`/`PHY/include`)로 한참 더 작업을 진행한 뒤 push 시점에야 뒤늦게 발견 — 히스토리가 크게 갈라짐.
**왜**: 작업 시작 시 `git fetch origin && git status`를 먼저 실행해 원격이 앞서 있는지 확인하는 절차가 없었음. 여러 세션/기기를 오가며 작업하는 구조상, 이 확인 없이는 로컬이 최신이라고 가정하는 것 자체가 위험함.
**적용**: 기능 자체(PUCCH/PRACH/PUSCH/MIMO/HARQ 등)는 로컬 WSL 작업이 최신이라고 판단해, 원격의 재구조화 히스토리는 `origin/archive/common-lls-sim-refactor` 브랜치로 보존하고 로컬 기준으로 `develop`을 force-push해 정리함. 이후 이 저장소의 `PHY/src`/`PHY/include` 평면 구조가 기준. 이 사고를 계기로 "작업 시작 시 항상 먼저 git fetch/status 확인" 규칙을 `CLAUDE.md`/`AGENTS.md`의 표준 절차로 고정함 — 매번 사용자가 요청하지 않아도 자동으로 수행할 것.

### 2026-08-03 — 종료된 Codex 대화는 복구 불가라고 단정하기 전에 로컬 세션 로그 확인
**무엇**: 터미널 종료 직전의 Tailscale/SSH 설정 대화를 기억하느냐는 질문에 처음에는 복구할 수 없다고 답했으나, 사용자 요청으로 `~/.codex/history.jsonl`과 `~/.codex/sessions/`를 확인한 결과 이전 세션 전문이 남아 있어 정확한 작업 지점을 복원할 수 있었다.
**왜**: 현재 모델 컨텍스트에 이전 대화가 없다는 사실과 로컬 디스크에 세션 기록이 없는지를 동일하게 취급했기 때문이다. Codex CLI는 종료된 세션의 입력과 응답을 로컬 JSONL로 보존할 수 있으므로 둘은 구분해야 한다.
**적용**: 사용자가 직전/과거 Codex 대화 복원을 요청하면 불가능하다고 단정하지 말고, 권한 범위 안에서 먼저 `~/.codex/history.jsonl`의 session ID와 `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl`을 읽기 전용으로 검색한다. 복원 시에는 사용자/assistant 메시지만 추출하고 토큰, 인증정보 및 내부 메타데이터는 노출하거나 기록하지 않는다.
